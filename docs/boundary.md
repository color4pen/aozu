# ツールの境界 — aozu が解く問題と解かない問題

対象読者: aozu の導入を検討・実施する人。個々の決定の正本は adr/ と docs/open-questions.md にあり、本書は誤解されやすい境界面だけを一枚に集約した要約である（各項に正本へのポインタを付す）。動詞の実装状況は README のステータスを参照。

## 問題のフレーム

aozu が解くのは「**設計文書が実装に追い越されて腐る**」問題である。設計文書そのものの生成・網羅・品質は対象ではない。強制する不変条件は design-not-later-than-merge の一つだけで、これを入口ゲート（request の引用検証）と出口ゲート（rules export → architecture test）で機械強制する（ADR-0007）。

一段抽象して言えば、管理対象は文書そのものではなく、文書間・文書とコード間の**辺**（参照・依存・引用）の総体である。辺はどの単一成果物にも属さず、維持の局所的動機を持たないため、放置すれば音もなく宙吊りになる——drift と呼ばれる現象の実体はこれである。aozu の機構はこの辺の実体化として読める: `[[id]]` は辺を一級の成果物にし、fail-closed は不可視の辺を禁止し、閉包規則の大半は辺の検証であり、入口ゲートは辺の維持に動機を与える。ただし閉包が検証するのは辺が**解決すること**までであり、両端が同じ理解を持つことではない（次節）。機械同士の辺の結合部にも暗黙の仮定は残り、統合の事故はそこで起きる（参考文献の architectural mismatch）。

**解く問題**:

- 設計正本の構造的整合（閉包）の決定的検証
- 構造に触れる変更が設計を経ずに merge されることの機械的な防止
- 設計要素の現在地の追跡（designed → requested → implemented、ADR-0005）
- 設計から request 草稿への導出支援と、その被覆の機械検証（plan / derive / coverage）

**解かない問題**:

- 設計内容の正しさ（良い設計かどうか。判断は人と、殻の外で走る LLM レビューの領分）
- 設計の網羅（システムの全側面を設計文書化すること。全量の書き起こしはアンチパターン — docs/adoption.md）
- 細部と実装の意味的整合（画面の項目・レイアウトが実装と一致しているか等。後述の三段選択）
- 実装の生成・agent 実行（文脈注入済みの指示を出力するまで。実行はセッション・パイプラインの領分 — ADR-0001）

## 「整合」の意味 — 構造であって内容ではない

check が検証するのは**閉包**である: ID が一意で、参照が実在要素に解決し、リンク義務が満たされ、manifest と整合していること（spec/format.md C1〜C12）。書かれた内容が正しいか、実装と意味的に一致しているかは検証しない。

**閉包 ≠ 網羅**。「まだ書かれていないもの」は check に映らず、check は書かれていないものについて嘘をつかない。書かれていない範囲は三分類で扱う（docs/adoption.md）: 静的構造の穴は機械が強制発見し、ゲートが触れた穴は需要駆動で埋め、触れていない穴は意図的に残る。網羅を主張する必要があるときは run 単位ではなく台帳単位で行う（docs/open-questions.md 論点 8）。

## 保証の対応表

保証は無条件には立たない。**manifest で enabled にした型 + 結線した歯**の範囲でのみ成立する（ADR-0010 の採用勾配。書き起こしと結線を分離しないこと — docs/adoption.md 原則 1）。

機械が保証すること:

| 保証 | 根拠 |
|---|---|
| 静的構造は常に全量・正確（未マップのソース・宣言外の依存は CI が落とす） | fail-closed、ADR-0007 出口ゲート、integration.md §3 |
| 設計を通した変更は実装に追い越されない（引用義務を課した request は設計要素を引用しない限り入口で弾かれる） | ADR-0007 入口ゲート、integration.md §1 |
| 設計正本の閉包（参照切れ・義務欠落・未知 prefix は check が落とす） | spec/format.md C1〜C12 |
| 要素状態の軌跡が残る（designed → requested → implemented が state.json に記録される。loop 有効時） | ADR-0005 / ADR-0018 |

人の判断のままのこと:

| 判断 | 置き場 |
|---|---|
| 何をどこまで設計要素にするか（網羅は強制されない） | 設計セッション |
| 要素の粒度（型ごとの主たる引用文脈で決める） | ADR-0017 |
| 設計内容の質・文書間矛盾の verdict（レビューは findings 列挙まで、採否は人） | topic / ADR |
| designed 要素を request へ束ねる判断 | plan |

## 細部の置き場 — 三段の選択

設計には細部（画面仕様・データ制約・API 形状など）へのニーズが実在する。aozu は「形式化するか、しないか」の二択ではなく、細部の置き場を三段階で選ばせる。判定基準は「**その細部を読む機械を名指しできるか**」（ADR-0004）。

| 置き場 | 機械との関係 | 使いどき |
|---|---|---|
| 1. 対象外（既存文書のまま） | 関知しない。資産マップに「どの型にも対応しない」と明示し、穴が意図的であることだけ記録する | 読む機械が無く、設計判断の材料としても運ばない細部 |
| 2. 要素の本文 | **検証されないが、利用される**。本文は prompt 注入でセッションに運ばれ、本文中の `[[参照]]` は check が解決を検証する。読み手は実装・導出を担う agent であり、運びたい文脈は厚く書いてよい（書かなければ運ばれない） | 機械検証はできないが、設計・導出の文脈として運びたい細部 |
| 3. ビュー型 + named consumer | 細部そのものを読む機械（例: permission → 権限マトリクスとコード定義の突合テスト）と同時結線して形式化する | 細部を読む機械を名指しできるとき（docs/adoption.md Step 4、ADR-0022） |

要素は「ID つき見出し + 自由な Markdown 本文」であり、骨格（ID・参照・リンク義務）だけが機械検証の対象になる。本文にどれだけ細かく書くかは自由で、書いた細部は腐りうるが、構造的な言及（`[[id]]`）だけは腐らない。

禁じているのは細部を書くことではなく、**検証されない細部を検証されているかのように扱うこと**だけである。screen ビューが有効化されていない（consumer 未特定 — ADR-0022）のは、この判定基準の適用例である。

## 既存ツールとの対応

導入検討時に「何を置き換え、何と併存するか」を誤解しやすいため、対応を明示する。aozu は検査の実行系を持たず、正本と契約成果物（rules.json・permissions JSON・CLI 契約）を供給する側に立つ——多くの既存ツールは競合ではなく**結線先**である。

| 既存のツール・実践 | 関係 | 既に使っている場合 |
|---|---|---|
| architecture test（dependency-cruiser / ArchUnit / import-linter 等） | **結線先**。出口ゲートの消費側そのもの（integration.md §3）。aozu は許可依存を rules.json として供給し、検査の実行はこれらの領分 | 手書きの規則定義を rules export からの生成に差し替える（docs/adoption.md Step 1） |
| ADR 管理（adr-tools / MADR 等） | **併存**。aozu が課すのは frontmatter の `topics:` 引用（C9、loop 有効時）のみで、ADR の書式・運用は制約しない | 既存の adr/ 資産はそのまま。loop 有効化の時点で `topics:` 引用だけ足す |
| consumer-driven contracts（Pact 等） | **将来の結線先候補**。リポジトリ境界をまたぐ辺の歯の先行例（docs/open-questions.md 論点 14）。現在の aozu の保証はリポジトリ内で閉じている | そのまま併用する。aozu の管理対象外の辺を既にカバーしている |
| 仕様駆動開発ツール（spec-kit / OpenSpec 等） | **別工程**。これらは変更単位の仕様 → 実装の工程を扱い、aozu は設計正本の構造整合と時間規律を扱う。重なるのは request 文書の受け口だけ | request 文書に引用欄と入口ゲートを結線すれば共存する（integration.md §1・§4、docs/adoption.md Step 2） |
| アーキテクチャ記述・図（Structurizr / C4 等） | **併存（挿絵扱い）**。aozu は図を検証対象にしない。構造の正本は modules.md / dependencies.md のテキスト | 図は残してよい。正本だけを static 層に移す（docs/adoption.md 原則 3） |

## 参考文献

- Naur, "Programming as Theory Building" (1985) — 設計の理解には文書に書き下せない残余があることの古典的論証。三段選択が「検証されない細部」を明示的に許容し、判断を人に残す理由
- Garlan, Allen & Ockerbloom, "Architectural Mismatch: Why Reuse Is So Hard" (1995) — 統合の失敗は型の不一致ではなく暗黙の仮定の食い違いで起きる。閉包検証を構造に限定し、内容の一致を保証と呼ばない理由
