## 1. 【最重要】seq の登場要素が mod 限定で、アクター（ロール）を書けない

- **仕様**: §12「本仕様内の未決」、§8（dynamic/seq スキーマ）、閉包規則 C5（登場要素はすべて mod に解決される）
- **書けなかったこと**: このシステムのシナリオの主役はロール（member / manager / finance / admin）と承認者・委任先である。「引合の案件化」は *誰が* できるか（convert は manager 以上）が業務の本質だが、C5 が登場要素を mod（コードのモジュール）に限定するため、seq にアクターを一切書けない。同様に「承認者が承認する」「委任先が代理承認する」の *主体* が消える。仕様 §12 が予告していた「業務系ではアクターが必ず登場する」問題が、最初の業務系シナリオで即座に顕在化した。
- **どう回避したか**: 全 seq の登場要素を mod のみで構成し、フローの主語を「UI が操作を送る」「usecase が認可を検証する」という *機構* の語りに翻訳した。アクターは各 seq 冒頭の散文で「登場要素に mod としては現れない（findings 参照）」と注記して逃がした。結果として seq はレイヤ間のデータ移送図になり、「誰の・何の業務か」という設計上最も重要な情報が形式から抜け落ちた。
- **提案（findings のみ。仕様は変更しない）**: act 型（アクター/ロール）の新設か、permission ビュー有効化を seq の前提にするか。少なくとも登場要素に mod 以外（act / perm / ext）を混在許可する余地が要る。§12 の二択（act 新設 vs ext/perm 前提）はこの対象では「act が要る」に傾く。ロールは画面や外部系より先に、シナリオの主語として必要になった。

## 2. 【最重要】認可（権限マトリクス）を置く場所がない

- **仕様**: §4 の型テーブル（perm は views 層）、manifest §3（ビュー型は enabled で有効化）、C11（層間参照方向）
- **書けなかったこと**: clearflow の認可設計（docs/design/03-authorization-design.md）は 10 個のエンティティ × 各操作 × 4 ロールの権限マトリクスで、コード上も `src/domain/authorization.ts` に一元定義された第一級の設計物である。これは permission ビュー（perm 型）の領域だが、指示によりビュー型は enable しない（かつツール未実装）。static/domain/dynamic のどの層にも「ロール × 操作 → 許可」を表現するスキーマがない。
- **どう回避したか**: 認可ロジックを持つ `authorization.ts` を独立モジュール `[[mod-authz]]` として static に立て、責務行に「ロール × 操作の権限マトリクスの一元定義と可否判定」と書いた。だがこれは *どこに認可があるか*（実装の所在）を記録できただけで、*権限マトリクスの中身*（誰が何をできるか）は 1 つも形式化できていない。設計の核心が丸ごと形式の外に残った。
- **所感**: 「ここでビューが欲しい」の最も強い箇所。permission ビューが無いと、業務 SaaS の設計は骨格の半分（プロセス）しか書けず、もう半分（権限）が書けない。

## 3. 【重要】画面・ユーザーゴール単位のユースケースを表現できない

- **仕様**: §4 型テーブル（scr / uc は views 層）、manifest §3
- **書けなかったこと**: clearflow には docs/design/screens/（11 画面仕様）と docs/usecases/（ユーザーゴール単位のユースケース 9 本）という充実した設計資産がある。screen（scr）・use-case（uc）ビューが未実装のため、これらを design/ に取り込めなかった。dynamic の seq はモジュール間シーケンスであって「ユーザーが達成したいゴール」ではなく、粒度も観点も異なる。
- **どう回避したか**: 取り込まず、manifest に「画面仕様・ユーザーゴール単位のユースケースは本形式では表現できない」と明記して除外した。既存の docs/design/ と design/ が二重管理になる構造的問題は残る（下記 8）。

## 4. 【重要】読み取り専用ドメイン（売上・通知・アクティビティ）が ent スキーマに馴染まない

- **仕様**: §8（domain/model.md — ent は「属性の箇条書き、関係は参照で表す」）
- **曖昧だったこと**: 売上（Revenue）・通知（DerivedNotification）・案件アクティビティ（DealActivityResult）は、永続エンティティを持たず他エンティティを横断参照して *読み取り時に構成される* 派生情報である。ent は「属性を持つ集約」を暗黙の前提にしており、「属性を持たず計算で構成される読み取りモデル」を表す語彙がない。これを ent として書くと、他の永続エンティティと見分けがつかず「属性の箇条書き」欄が埋まらない。
- **どう回避したか**: 売上のみ `[[ent-revenue]]` として ent に置き、本文で「独自の永続エンティティを持たず横断参照する」と断った。通知・アクティビティは ent 化せず用語集の `[[term-timeline]]` に構造無しの語彙として逃がした（dataflow / event ビューが本来の置き場と思われる）。ent と read-model の区別を形式が持たないため、判断が恣意的になった。

## 5. 【重要】ドメインイベントと監査ログ——「横断的メカニズム」を層に置く歪み

- **仕様**: §8（static/modules.md — mod は実装ディレクトリに接地）、C11（層間参照方向）
- **書けなかった/歪んだこと**: ドメインイベント機構・監査記録（recordAudit）・認可は、レイヤードの一方向スタックに乗らない横断的関心事である。イベントは domain に型があり infrastructure にハンドラがあり application が発行する。形式は mod を実装ディレクトリに 1 対 1 で接地させる（`実装:` 行）ため、この「複数層にまたがる 1 つの機構」を単一 mod で表せない。
- **どう回避したか**: 機構を実装ディレクトリ境界で分割し、`[[mod-event]]`（domain/events/）と `[[mod-handler]]`（infrastructure/handlers/）に割った。概念は 1 つ（イベント駆動）だが mod は 2 つになり、「イベント機構」という設計単位が形式上は 2 つの無関係なモジュールに見える。ドメインイベント自体は `[[ent-domain-event]]` として domain にも二重に現れる（機構 = mod、事実 = ent）。

## 6. 【中】1 ユースケース 1 関数だが mod は 1 ディレクトリ——粒度の作業仮説の検証点

- **仕様**: §8、粒度作業仮説「引用される最小単位」（docs/open-questions.md §3）
- **迷ったこと**: clearflow の application/usecases/ には 130 以上の関数ファイルがある（createDeal, approveRequest, ...）。粒度仮説「引用される最小単位」に従うと、seq の登場要素で個別 usecase（updateInquiryStatus 等）が名指しされるので、1 usecase = 1 mod にすべきとも読める。だが dependencies.md の許可依存は 130 モジュール × 相互で官僚制的に爆発する。
- **どう仮決めしたか**: mod は「レイヤ/ディレクトリの seam」粒度（`[[mod-usecase]]` = usecases/ ディレクトリ全体）とし、個別 usecase は seq 本文の散文で名指し（例: 「updateInquiryStatus を呼ぶ」）するに留めた。**これは粒度仮説の反例**: seq は個別 usecase を引用したがる（→ 仮説では細分化を示唆）が、dependencies の許可依存は粗い単位でしか機能しない（→ 粗い単位を要求）。同一の mod に対し「引用される最小単位」が用途（seq vs dependencies）で食い違う。仮説は mod には素直に効かない。inv には効いた（下記 7）。

## 7. 【中】粒度仮説は inv では支持された

- **仕様**: §8（inv は 1 見出し 1 本）、粒度作業仮説
- **観察**: 不変条件は 23 本すべてが「1 見出し 1 本」で自然に切れ、各々が seq やエンティティ本文から個別に引用されうる粒度に収まった（例: `[[inv-contract-requires-won-deal]]` を seq-contract-creation の文脈で単独引用できる）。状態遷移ルールを inv に切り出す方針も、「converted は終端」「終端フェーズは不可逆」のように 1 ルール 1 見出しで破綻しなかった。**粒度仮説は inv・ent では素直に支持された**が、mod では用途間で食い違った（6）。仮説の妥当性は要素型に依存する、というのが検証所感。

## 8. 【中】既存 docs/design/ と design/ の二重管理——brownfield 導入経路の未整備

- **仕様**: ADR-0010（in-place 形式化）、docs/open-questions.md §6（brownfield 導入経路）
- **問題**: clearflow は既に docs/design/（ドメイン・承認・認可・アーキ・データモデル・UX・画面）と docs/usecases/ に完成度の高い設計資産を持つ。aozu の design/ を新規に書き起こすと、同じ設計が 2 箇所に分散する。open-questions §6 は「既存設計文書のその場での形式化」を入口とするが、既存文書に ID を振って形式化する具体手順（コマンド）が無いため、実際には並行別文書を新規作成する形になった。既存資産のある brownfield ほど二重管理コストが顕在化する。
- **どう回避したか**: 制約に従い design/ に新規作成のみ。既存 docs/design/ は一切触らず、findings に構造的問題として記録。

## 9. 【小】term と ent の非重複ルールで「商談」の置き場が縮約された

- **仕様**: §8（ent の見出しは用語定義を兼ねる。glossary には構造を持たない語彙のみ）
- **迷ったこと**: 「商談」はこのドメインの一級用語だが、独立エンティティではなく「関連先が案件/引合の顧客接点（Interaction）」という *Interaction の一部分集合* である。ent にすると `[[ent-interaction]]` と概念重複し非重複ルールに反する。term にすると構造（営業ステージ meetingType・HearingData）を持つので「構造を持たない語彙のみ」に反する。
- **どう仮決めしたか**: `[[term-shodan]]` を term に置き、構造の詳細は `[[ent-interaction]]` 側に寄せて term 本文からは参照で繋いだ。「エンティティの部分集合に固有の用語」を term/ent のどちらとも言い切れないケース。非重複ルールは「1 概念 1 要素」を前提とするが、業務ドメインには「既存エンティティの文脈的サブタイプ」（商談 = 特定 relatedTo の Interaction）が頻出し、この前提が緩い。

## 10. 【小】値オブジェクトに ID を振らない判断は粒度仮説どおり収まった

- **仕様**: §8、粒度仮説「単独で引用されることが一度もない要素は細かすぎ」
- **観察**: InquirySource / DealPhase / ContractStatus / MeetingType / PolicyCondition などの値オブジェクトは多数あるが、いずれも単独で request や seq に引用される見込みがなく、親エンティティ本文に列挙で畳んだ（例: 案件の phase を `[[ent-deal]]` 本文内に列挙）。粒度仮説「単独引用されないなら細かすぎ」に素直に従えた数少ない箇所で、迷いは無かった。仮説がクリーンに効く領域（値オブジェクト）と食い違う領域（mod）が分離できたのは収穫。

## 11. 【小】非正規化・DB制約など「実装都合の設計」を書く欄がない

- **仕様**: §8（ent スキーマ）、C11
- **曖昧だったこと**: contracts.clientId は Deal 経由で取得可能だが JOIN 削減のため非正規化保持、interactions の関連先 CHECK 制約、deals_inquiry_id_unique 一意制約——これらは設計判断だが「エンティティの属性」でも「不変条件」でもなく、DB スキーマ（`[[mod-db]]`）の実装詳細に属する。ent 本文に混ぜると純粋なドメイン語彙が汚れ、inv に書くと業務ルールと実装最適化が混在する。
- **どう回避したか**: 業務ルールとして意味を持つもの（1 引合 1 案件・関連先必須）は inv に昇華し、純粋な最適化（clientId 非正規化）は ent 本文の括弧書きに留めた。data ビュー（dat 型）が本来の置き場と思われるが未実装のため、判断が都度手動になった。
