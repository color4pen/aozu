# aosora ドッグフーディング findings（2026-07-04）

出所: aosora（greenfield SNS。design/ フルループ + spec-runner designLayer 結線を day 0 から有効化した最初のプロジェクト）での実運用。foundation request の一周（topic → 設計 → plan → derive → coverage → run → merge → mark implemented）と social request の進行中に、実施者（agent セッション）が踏んだ摩擦の一次報告 + 本リポジトリ側での裏取り。

判定の分類: **設計課題**（仕様の判断が要る → open-questions へ）/ **バグ**（仕様と実装・ガイダンスの不整合 → 修正 request へ）/ **ergonomics**（CLI 使い勝手 → 修正 request へ）/ **誤解**（ツール側は正しい。文書で補う）。

## 1. `[[id]]` が「被覆宣言」と「依存参照」を兼ねる — 設計課題（最重要）

social request が実装済みの [[ent-user]] / [[ent-post]] を「依存する文脈」として引用したところ、`check --request` の R2（implemented 要素の引用は不合格）で弾かれた。挙動は仕様どおり（integration.md §1: 引用は被覆の宣言であり、変更しない要素の文脈引用には使わない）だが、**「この request が変更しない依存」を宣言する場所が存在しない**。現運用の回避策はコード表記（`` `ent-user` ``）で参照抽出から除外することだが、非自明で、依存情報が機械可読でなくなる。

→ **open-questions 論点 13 に起票**（設計候補の比較が要る。ADR 級）

## 2. scaffold の ID 二重指定 — ergonomics

`aozu scaffold topic concept` は失敗し、`aozu scaffold topic top-concept` が要る。type を指定しているのに id にも prefix を要求するのは冗長で、初見で詰まる。

→ **修正**: document 型（topic / plan / seq / adr）で prefix 無しの slug を受けたら自動補完する（フル id も引き続き受理）

## 3. C9 と `topics:` frontmatter の「二重要件」— ガイダンスのバグ（実害あり）

報告は「`topics: top-concept` を frontmatter に書いても本文に `[[top-concept]]` が無いと C9 で落ちる。両方要る理由が読めない」。裏取りの結果、**二重要件は存在しない**——正書式はブラケット付き `topics: [[top-concept]]` であり（spec §8・scaffold テンプレ・addressed 導出・C9 のすべてが一貫）、frontmatter 一箇所で C9 も addressed も満たせる。真の原因は **prompt session の SESSION_GUIDANCE が plain 形式 `topics: top-my-topic` を例示している**こと（src/prompt/session.ts）。この例に従うと C9 で落ち、本文引用で回避しても **addressed 導出が静かに失敗する**（実害: aosora の top-concept は解決済みのはずが status で Open のまま）。

→ **修正**: SESSION_GUIDANCE の例をブラケット形式に統一 + C9 診断メッセージに正書式の助言を含める

## 4. derive の前提配線が発見しにくい — ergonomics

manifest に `request-template` / `request-output-dir` が無い状態で `prompt derive` が 2 回 config エラーになってから配線に気づいた。`aozu init` は static 最小プロファイルを生成するため、loop 有効化後に必要になる導出配線への導線が無い。

→ **修正**: derive の stage-gate エラーに「manifest frontmatter に何を書くか」の具体的修正手順を含める + init が生成する manifest テンプレのコメントに導出キーの説明を追記

## 5. mark implemented の引数形式 — 半分は誤解

「`mark implemented foundation` ではなく `--request foundation` が要る。--help が詳細を出さない」。後半は誤解（`aozu mark implemented --help` は全オプションを表示する。`aozu mark --help` が要約のみ）。前半は妥当な ergonomics。

→ **修正**: positional slug を受理（`mark implemented <slug>` ≡ `--request <slug>`）+ `mark --help` の要約に主要オプションを併記

## 6. format-version の検証フェンスが無い — バグ（fail-closed 違反）

本リポジトリ側の追加検査で発見: `format-version: 99` の design/ を check が**無診断 exit 0 で通す**。manifest パーサ（src/check/manifest.ts）は値を読むだけで、ツールの対応バージョン集合と照合していない。fail-closed 原則（未知は違反）に反し、将来の format-version 増分時に「旧ツールが新形式を黙って誤読する」事故経路になる。移行機構（論点 7）の前提となるフェンス。

→ **修正**: manifest の format-version が対応集合（現在 `{"0"}`）に無ければ error（全動詞共通の入口で判定、対応集合は定数一箇所）
