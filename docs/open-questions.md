## 8. プロンプト注入のスコープ規則

設計が大きくなると `prompt session` / `prompt propagate` の注入文脈がコンテキストに収まらない。関連要素の参照グラフ近傍だけを注入するスコーピング規則が要る。

**初版実装済み**: `prompt session` が本規則案（2 hop・inv/term 全量・static 縮約）を実装した。規則値は src/prompt/session.ts の定数 `SESSION_MAX_HOPS` に集約されている。「manifest の要約」は enabled 一覧のみの注入という縮小解釈で実装している（session は request-template 等の消費者設定に依存しない — prompt-session change の設計判断 D8）。高度化（戦略 3）は窓に収まらなくなった実例の証拠を待つ。

規則案（実装時に調整）: 対象要素（topic / ADR が引用する要素）+ 参照の in/out 2 hop 近傍を本文ごと注入。不変条件と用語集は常に全量（小さく、常に判断material になる）。manifest と形式規則の要約は常に注入。static のモジュール一覧は見出し + 責務行のみの縮約形。

**窓の制約下で網羅を達成する戦略**（窓が禁じるのは「一回の実行での網羅」であり、網羅そのものではない。検証の被覆も設計と同じく積み重ねるものとして扱う）:

1. **母集団の機械列挙**: 検証対象の全体（要素・文書・仕様の節）は parse で決定的に列挙できる。網羅の定義はこの母集団に対して行う
2. **被覆台帳**: 検証単位 = シャード × 観点レンズのマトリクス。各セルに検証時点の内容ハッシュを記録し、変更されたセル + 参照グラフ近傍を自動無効化して再検証フロンティアに落とす。**「網羅」= 検証フロンティアが空、という台帳の状態**（designed → requested → implemented と同型の状態機械）。まず `docs/review/coverage.md` の運用台帳で始め、形が固まったら review-state sidecar + status の検証フロンティア表示としてツールに昇格する
3. **ペアの 2 段階照合**: 矛盾は文書ペア間に出る（素朴には O(n²) 窓）。各文書から主張の索引（1 行主張リスト）を窓内で抽出し、小さい索引同士を全ペア照合、疑わしいペアのみ本文精読。グラフ接続ペアは近傍シャーディング、グラフ外の意味的衝突を索引層が拾う
4. **規則への卒業 = 台帳の縮小**: 決定的規則（C 規則・歯・conformance テスト）に卒業したクラスは窓なしで全量恒常検証になり、LLM マトリクスから恒久に消える。台帳は「未機械化の検証残額」の可視化を兼ねる
5. 現在形の正本を小さく保つ（ADR-0004 の分離は窓対策でもある）。仕様が窓に収まらなくなったら設計の警報
6. 網羅の主張は **run 単位ではなく台帳単位**で行う。個々の run は担当シャードと「見ていない範囲」を明示する（findings ゼロと未走査の区別）。大域の品質・方向は人の領分

## 9-a. one-shot runner の要否

プロンプト動詞を設定コマンドテンプレートで直接実行する薄い runner（同期一発・agent 出力を解釈しない・合否は check / coverage）を持つか。主経路が「agent セッションが aozu を呼び、出力された指示を消費する」である間は不要。セッション外での一括 derive 等の需要の証拠が出たら再検討する。持つ場合も、オーケストレーション状態（queue / worktree / resume / 自動リトライ）は workflow ツールの領分であり aozu に足さない。

## 14. 境界をまたぐ辺 — 外部面の宣言と互換の時間規律

fail-closed（「列挙されない依存は禁止」）の現在の到達域はリポジトリ内で閉じている: rules export → architecture test が検証するのは mod 間の依存であり、リポジトリ境界をまたぐ辺には宣言の場所がなく、check にもゲートにも映らない。「構造に触れる変更が設計を経ずに merge されない」という不変条件が、境界をまたぐ辺には課されていない。

境界をまたぐ辺は双方向ある:

- **依存する外部面**（outbound）: 外部 API・外部サービスへの依存。drift の被害者は自プロジェクト
- **提供する外部面**（inbound）: 自プロジェクトが公開する機械向けの面（REST API・MCP サーバ・webhook）。drift の被害者はリポジトリ外の消費者であり、リポジトリ内の architecture test には構造的に映らない

需要の証拠（2026-07-09 記録）: clearflow は MCP サーバ（deals / invoices / approval_policies 等のツール群）を公開しており、提供面の実需は仮説ではなく現物。MCP クライアント（agent）はアクターであり、act 型の既存語彙で受かる——ツール露出 × アクターの照合は permission ビューの検証対象に含めるべき辺になる（clearflow findings 2 と接続）。依存面（outbound）の実需はまだ findings に記録がない。

内部辺との本質的な差は二つ:

- **実在の検証ができない**。境界の向こうの現物（外部端点・外部消費者）は CI の管轄外にあり、検証できるのは「宣言と、チェックイン済みの契約成果物（OpenAPI・tool schema・型定義等）との整合」まで
- **互換性は時間の関係**。壊れるのはバージョン間であり、現在形のコードには映らない。歯は契約成果物の差分（互換 diff）に付けるしかない。提供面では「自分の変更が外部消費者を壊さないか」、依存面では「相手の変更に気づけるか」と、時間規律の向きが反転する

決めること:

- 対象とする外部辺のクラス（依存面だけか、提供面・パッケージ・外部 SaaS まで含むか）
- 宣言の置き場。三段選択（docs/boundary.md）と同じ分解が有力: 実体（契約成果物）はコード側、決定（採用・互換方針）は ADR / inv、**存在の宣言**（この mod はこの外部面に依存する / を提供する）だけを static 層に追補する
- 歯: チェックイン済み契約への CI 互換 diff・契約テスト（consumer-driven contracts が先行例）。named consumer を名指しできないクラスは追補しない（ADR-0004 / ADR-0022 と同じ関門）

宣言構文・閉包規則の追補は spec に触れるため、決着後に設計 delta → request の正規経路で実装する。

## 15. MCP 表面 — 交換面契約の第二表面

交換面契約（spec/integration.md）は CLI 表面で定義されている。CLI は一枚の表面に機械向けの辺（exit code・構造化出力）と agent 向けの辺（診断文・instruction）が同居しており、消費者はどちらを読むかを暗黙に選んでいる。MCP はこの分離（tool schema = 機械の辺 / description と出力テキスト = agent への帯域）をプロトコル構造として最初から持つため、対応は新設計ではなく既存契約の再配置になる。

決めること:

- integration.md の契約を第二表面としてどう二重化するか（CLI を plumbing、MCP を porcelain とする分離。git の前例）
- tool description の設計。三段選択の第 2 段（本文 = agent への帯域）と同じ性格を持ち、読み手が agent である以上、到達率という経験的な歯を付けうる
- 起動のトリガ。主経路（agent セッションが CLI を呼ぶ）で足りている間は急がない（論点 9-a と同じ判定）。実装して契約が軋んだ箇所は、機械の辺 / agent の辺の分類の診断信号として扱う

## 16. リスク駆動の先回り — 需要駆動の事後性への例外

追補・結線のトリガは一貫して需要駆動である（ADR-0022: named consumer が立つまで追補しない）。だが需要シグナルは実地では**事故として届く**ことがある: 「consumer が要求された」の最初の形が、権限漏れや課金誤りというインシデントになりうる。需要駆動は構造的に事後的であり、一回目の失敗が高くつく辺のクラスでは、歯が一件分だけ遅れて到着する。

例外の適用範囲を絞る判定基準（三項の積）:

1. **意図の非記録性**: その結合が正しいかの判断材料が、どの成果物にも書かれていない度合い（認可の意図はコードに現れない。Naur "Programming as Theory Building" 1985 が言う、書き下せない理解の残余）
2. **帰結の高さ**: 失敗のコスト（権限・課金・データ保持は不可逆または高額）
3. **失敗の沈黙性**: 自己申告しない度合い。視覚の失敗はユーザーの目という常時稼働の検出器があり自己申告するが、認可の失敗は誰にも見えないまま稼働し続ける

三項がすべて高いクラス（permission・課金・データ保持・アクセシビリティ）に限り、needs-consumer の**起動タイミングだけ**を例外とする——consumer の名指しは先回りでも省略しない（例: permission → 権限マトリクスとコード定義の突合テスト。ADR-0022-3 が予告する一件目と同じ形）。視覚詳細は 1 が高くても 3 で落ちるため対象外となり、既存の決着（ADR-0022 Context）と整合する。

論点本体: この例外を認めるか。認める場合、ADR-0022 の補記（または改訂 ADR）として記録し、三項基準を判定の言葉として明文化するか。
