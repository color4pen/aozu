# 未確定の論点

決定済み事項は adr/ を参照。ここは詰め残しの一覧。解決したら ADR 化または形式仕様へ反映して消す。

## 1. 名前

`sd` は仮称。同名の著名 CLI（sed 代替の Rust 製ツール）と衝突するため、npm publish 前に binary 名を確定する必要がある。

## 2. 形式仕様の実体（最大の残作業）

ADR-0003 は方針のみ。次を仕様として起草する:

- ID 文法の正確な定義（文字集合・型プレフィクス一覧・一意性スコープ）
- 見出し規約・frontmatter スキーマ（アーティファクト型ごと）
- manifest スキーマ（ビュー有効化・リンク義務・前提ビューの宣言形式）
- 実装状態マップの格納形式
- plan / topic のスキーマ

## 3. 要素の粒度

何に ID を振るか（エンティティ単位か属性単位か、不変条件 1 本ごとか、シーケンス単位かステップ単位か）。細かすぎると官僚制、粗すぎるとトレースが無意味。**実プロジェクト適用でしか決まらない**ため、最初のドッグフーディング対象の選定とセットで決める。

## 4. 状態マップの並列衝突

並列 request 実行時に実装状態マップが同一ファイルで merge 衝突する可能性。1 ファイル集中か要素分散か、追記型か。形式仕様（論点 2）の一部として詰める。

## 5. 実装パイプライン側の受け口

- request 検証からの `check --request` 呼び出し（入口ゲート）
- 取り込み完了時の `mark implemented` hook（出口の状態遷移）
- request テンプレートへの設計要素引用欄の追加

いずれ実装パイプライン側への変更 request として起票する。

## 6. brownfield 導入経路

既存コードベースへの `init`。設計文書ゼロの状態から、既存コードの偵察を経て初期設計文書（特に静的構造と許可依存）を起こす手順。attended セッション + プロンプト同梱で足りるか、専用の導入手順が要るか。

## 7. 形式のバージョニングと移行

strict プロファイルや manifest スキーマが変わったときの既存プロジェクトの移行手段。manifest にスキーマバージョンを持たせるか。

## 8. プロンプト注入のスコープ規則

設計が大きくなると `prompt session` / `prompt propagate` の注入文脈がコンテキストに収まらない。関連要素の参照グラフ近傍だけを注入するスコーピング規則が要る。

## 9. 最初のドッグフーディング対象

形式は実使用でしか固まらない。候補: 本ツール自身（小さすぎる可能性）、既存の実装パイプラインプロジェクト（architecture/model.md と歯が既にあり、移行の題材として最適だが規模が大きい）。
