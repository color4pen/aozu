# 未確定の論点

決定済み事項は adr/ を参照。ここは詰め残しの一覧。解決したら ADR 化または形式仕様へ反映して消す。

## 1. 名前

`sd` は仮称。同名の著名 CLI（sed 代替の Rust 製ツール）と衝突するため、npm publish 前に binary 名を確定する必要がある。

## 2. 形式仕様の実体（最大の残作業）

ADR-0003 は方針のみ。次を仕様として起草する:

- ID 文法の正確な定義（文字集合・型プレフィクス一覧・一意性スコープ）
- 見出し規約・frontmatter スキーマ（アーティファクト型ごと）
- manifest スキーマ（ビュー有効化・リンク義務・前提ビューの宣言形式）
- 実装状態マップの格納形式
- plan / topic のスキーマ

## 3. 要素の粒度

何に ID を振るか（エンティティ単位か属性単位か、不変条件 1 本ごとか、シーケンス単位かステップ単位か）。細かすぎると官僚制、粗すぎるとトレースが無意味。**実プロジェクト適用でしか決まらない**ため、ドッグフーディング（論点 9）とセットで決める。

作業仮説（ドッグフーディングで反証可能）: **粒度 = 引用される最小単位**。単独で引用されることが一度もない要素は細かすぎ、request が要素の一部だけを対象にし始めたら粗すぎ。この基準から、不変条件は 1 本 1 要素（番号で個別引用される）、エンティティ属性はエンティティ単位（単独で request にならない）が導かれる。

## 4. 状態マップの並列衝突

並列 request 実行時に実装状態マップが同一ファイルで merge 衝突する可能性。1 ファイル集中か要素分散か、追記型か。形式仕様（論点 2）の一部として詰める。

## 5. 実装パイプライン側の受け口

- request 検証からの `check --request` 呼び出し（入口ゲート）
- 取り込み完了時の `mark implemented` hook（出口の状態遷移）
- request テンプレートへの設計要素引用欄の追加

いずれ実装パイプライン側への変更 request として起票する。

## 6. brownfield 導入経路

入口は ADR-0010 で決定済み: 最小プロファイル（静的構造のみ）+ 既存設計文書のその場での形式化。残る問いは手順の具体:

- 設計文書ゼロのコードベースから静的構造を起こす偵察プロンプトの同梱
- 手製の architecture test からの rules export への差し替え手順
- 既存文書への ID 付与を支援するコマンドの要否

## 7. 形式のバージョニングと移行

strict プロファイルや manifest スキーマが変わったときの既存プロジェクトの移行手段。manifest にスキーマバージョンを持たせるか。

## 8. プロンプト注入のスコープ規則

設計が大きくなると `prompt session` / `prompt propagate` の注入文脈がコンテキストに収まらない。関連要素の参照グラフ近傍だけを注入するスコーピング規則が要る。

## 9. ドッグフーディング計画

方針は決定済み。3 対象がそれぞれ別の仮説を検証する:

| 対象 | 検証するもの | 位置づけ |
|---|---|---|
| 本ツール自身 | 文法が回るか（ID・参照・check・self-hosting の閉包） | bootstrap。要素数が少ないため**粒度の結論は引き出さない** |
| 業務 SaaS（ドメイン・画面・ユースケース・権限を持つ Web アプリ。実装パイプライン適用済み） | 粒度（論点 3）とフルループ（topic → 設計 → plan → request → run → implemented）の一周 | 本番検証。粒度の摩擦は一周回さないと出ない |
| 実装パイプラインプロジェクト自身 | 段階①の in-place 形式化（ADR-0010）。architecture フォルダへの ID 付与と rules export への差し替え | 最小プロファイルの検証。範囲が小さいので時期は柔軟 |

残: 実施順の最終確定と、各対象での着手時期。
