# 導入経路 — 既存プロジェクトへの書き起こしフロー（draft）

対象読者: aozu を既存プロジェクト（brownfield）に導入する実施者。greenfield は scaffold から始めれば Step 1 以降と同じ形になる。

本書は ADR-0010（採用勾配）と ADR-0004（生きた文書は読む機械を持つ）の運用手順である。

## 三原則

1. **消費者と同時にしか書き起こさない**。書き起こしの単位は「型 + その型を読む機械の結線」であり、結線を伴わない書き起こしは行わない。読む機械のない文書は腐る（ADR-0004）
2. **一括で書き起こすのは static のみ**。domain / dynamic / views の一括転写は行わない。request が触る近傍を、その request の準備として書き起こす（需要駆動）
3. **正本は型ごとに移る**。manifest で enabled にした型が扱う事実は design/ が正本となり、既存文書の該当箇所は design/ へのポインタに置き換える（削除しない）。enabled でない型の事実は既存文書が正本のまま。同一の事実に正本を 2 つ置かない

各型の「読む機械」:

| 型 | 読む機械（結線先） |
|---|---|
| static（mod / 許可依存） | rules export → architecture test（CI） |
| domain（term / ent / inv / act） | 入口ゲート `check --request`（request の引用検証）と prompt 注入（term / inv は常時全量） |
| dynamic（seq） | 同上（request の引用の的） |
| loop（top / plan / state） | status のフロンティア表示・derive・mark |
| views | 型ごとに個別の named consumer（例: permission → 権限マトリクスとコードの権限定義の突合テスト）。consumer が名指しできるまで有効化しない |

## フロー

各 Step は 1 セッションで完結する分量に切る。セッションは使い捨てでよい——状態はすべてリポジトリに落ち、`status` と check の診断で現在地が復元できる。実施者は開発の経緯を知らなくてよい（本書と spec/format.md で閉じる）。

### Step 0 — 偵察と資産の棚卸し（1 セッション、書き起こしなし）

1. 対象の構造（モジュール分割・依存方向・ドメイン概念）を読む
2. 既存設計文書を棚卸しし、**資産マップ**を作る: 文書（節）ごとに「どの型に対応するか / どの型にも対応しない（そのまま残す）か」を列挙する
3. manifest を起案する。enabled は最小（まず `static`）

成果物: manifest.md + 資産マップ（docs/ 配下の 1 ファイル。以後の需要駆動充填の索引になる）

### Step 1 — static の書き起こしと歯の結線（1 セッション、1 PR）

書き起こしと強制力の結線を**同じ PR** に載せる。書き起こしだけが先に merge された状態を作らない。

1. `static/modules.md`: mod は **seam 粒度**（レイヤ / ディレクトリ境界）で切る。個別関数を mod にしない（許可依存が爆発する）。全 mod に責務 1 行 + `実装:` 行
2. `static/dependencies.md`: 現状の依存を許可依存として列挙する。列挙外は禁止になる
3. `export rules` → rules.json をコミット → architecture test を CI に結線。実装ディレクトリの未マップファイルは fail-closed（テスト側の義務。integration.md §4）。手製の architecture test が既にある場合はこのテストへ差し替える

受け入れ基準（すべて機械検証）:

- `check` exit 0
- architecture test green（CI 上）
- 実装ディレクトリに rules.json の paths でマップされないソースが存在しない

以後、静的構造の穴（新規モジュール・未宣言依存）は機械が強制発見する。人が探す必要はない。

### Step 2 — 作業サイクルへの結線（1 PR）

request（変更の入口）に設計を接続する:

1. request テンプレートに設計要素の引用欄を設ける
2. request 検証に `check --request` を組み込む（引用 ID の実在検証。入口ゲートの強制力は呼び出し側の結線が所有する — ADR-0007）

実装パイプライン（spec-runner 系）を使うプロジェクトでは、この結線はパイプライン側の受け口として実装される（docs/open-questions.md 論点 5）。

以後、「設計に触れない変更」が機械に見える。ここが design-not-later-than-merge の起点。

### Step 3 — 需要駆動の充填（定常運用）

domain / dynamic は request の準備の一部として書く:

1. request が触る近傍（用語・不変条件・エンティティ・シーケンス）に要素が無ければ、資産マップから該当する既存文書を探し、その範囲だけ design/ に書き起こす
2. 既存文書の該当箇所は design/ へのポインタに置き換える（原則 3）
3. 1 穴 = 1 使い捨てセッション。書き起こした範囲で `check` exit 0 を確認して閉じる

例外として、**term / inv は需要を待たず先行して書き起こしてよい**: 小さく、prompt 注入で常時全量が読まれるため、消費者が既に居る（原則 1 に適合する）。domain を有効化した時点で用語集と不変条件だけは既存文書から起こす価値がある。

### Step 4 — ビュー（named consumer が現れたときのみ）

ビューの有効化・移行は「そのビューを読む機械（または強制力）」を名指しできるときに限る。consumer を先に構想し、ビューの書き起こしと consumer の結線を同じ PR に載せる（Step 1 と同じ形）。

## check exit 0 の意味

check が検証するのは**書かれたものの閉包**（参照が解決し、義務が充足していること）であり、設計の網羅ではない。「まだ書かれていないもの」は check には映らない。書かれていない範囲の扱いは三分類で明示する:

1. **静的構造の穴**: 機械が強制発見する（Step 1 の歯。fail-closed）
2. **ゲートが触れた穴**: 需要駆動で埋める（Step 3）
3. **触れていない穴**: 意図的に書かれないまま置く。閉包は「書かれていないもの」について嘘をつかない

網羅を主張する必要があるときは run 単位ではなく台帳単位で行う（docs/open-questions.md 論点 8）。

## アンチパターン

- **一括転写**: domain / dynamic / views を最初に全部書き起こす。消費者が居ないまま量だけができ、腐る。ドッグフーディング（仕様の破綻を発見するのが目的。docs/dogfooding-runbook.md）では一括転写が正当だが、導入（運用が目的）では逆
- **書き起こしだけの PR**: 歯・ゲートの結線を「あとで」に分離する。結線されるまで正本は拘束力を持たず、その間の変更が正本を古くする
- **既存文書の一括削除・一括移行**: 正本の移管は型ごと・需要ごとに行う。enabled でない型の事実まで動かすのはセレモニー
- **1 セッションでの継続作業**: 複数 Step・複数の穴を同一セッションで続けると文脈が枯渇する。状態はリポジトリにあるので、切ってよい
