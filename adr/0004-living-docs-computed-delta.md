# ADR-0004: living docs 正本・delta は計算物

- Status: accepted（補記 2026-07-09: 「読む機械（または強制力）」の三分類を末尾に追加。決定は不変）
- Date: 2026-07-02

## Context

delta（変更フォルダ）を成果物として維持し、適用・archive する方式の仕様管理ツール（openspec 系）の運用経験では、統合後の仕様が陳腐化した。根因は 2 つ:

1. **人間しか読まない文書は、参照されなくなった日から腐る**。乖離にコストが付かない
2. 「適用待ち delta」という**維持責任のある中間成果物**が増え、それ自体が陳腐化の対象になる

## Decision

- **正本は常に現在形の設計文書（living docs）**とする
- **delta は計算物**。git ref 間から ID ベースで算出する（`diff` コマンド）。維持する成果物としての delta（変更フォルダ）を作らない
- 過去形の記録は **ADR のみが積層**する。ADR は判断の記録であり、現在の設計を読むために必要なものにしない
- 陳腐化対策として**設計文書に機械の読者を付ける**:
  - 許可依存の rules export → 実装リポジトリの architecture test が消費し、乖離で CI が赤くなる
  - request 入口ゲート → request が引用する要素 ID の実在を検証する
  - coverage / status → 導出漏れ・状態の淀みを常時可視化する

## Consequences

- 「適用待ち」という状態が存在せず、設計文書は常に読んだ通りが正
- 設計と実装の乖離に即座に機械的コストが付くため、参照され続ける構造が維持される
- 差分の意味づけ（なぜ変えたか）は git diff からは出ないため、ADR が担う

## 補記（2026-07-09）: 「読む機械（または強制力）」の三分類

本 ADR の判定基準（形式化は読み手を名指しできるときのみ）が言う読み手は三種に分けられ、いずれを名指しできても形式化は正当化される:

1. **決定的な歯** — exit code で合否を返す機械（check・conformance テスト・CI 突合）。verdict を持てる唯一の身分
2. **助言的な機械** — LLM レビュー・agent セッション。読んで findings を列挙するが、verdict は持たない（採否は人 — docs/boundary.md）。非決定的な読み手に verdict を与えると、検証対象がモデルの癖への適合に最適化されうる（Goodhart）。助言的身分は能力の不足ではなく構造の選択である
3. **強制力** — 監査・契約・規制。機械ではないが読み手として実在し、named consumer の資格を持つ

なお「書き下せない理解が残る」こと自体の古典的論証は Naur "Programming as Theory Building"（1985）。本 ADR の陳腐化対策は、書き下せる部分に読み手を付ける話であり、書き下せない残余を消す話ではない。
