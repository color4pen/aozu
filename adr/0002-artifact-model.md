# ADR-0002: 成果物モデル — コア 3 層固定 + ビュー可変

- Status: accepted（「コア 3 層は常時有効・必須」は ADR-0010 により修正: 最小プロファイルは静的構造のみ。段階は ①静的 → ②+ドメイン・動的 → ③+loop → ④+ビューであり、詳細は ADR-0010 が正）
- Date: 2026-07-02

## Context

必要な設計文書はプロジェクトの性質で変わる。Web アプリには画面設計が要り、ライブラリは API surface が本体で、バッチ基盤はデータフローが本体になる。成果物集合を固定すると汎用性を失う。

一方で成果物集合を完全可変にすると「設計が閉じている」の定義まで可変になり、閉包検証と両立しない。またアーティファクト型をユーザー定義できるメタフレームワークは、設定を書かないと始まらないツールになり「install してすぐ使える」方針に反する。

## Decision

**コア 3 層を常時有効・必須**とする。ソフトウェアの性質によらず普遍であるため:

| 層 | アーティファクト |
|---|---|
| ドメイン | 用語集 / ドメインモデル（エンティティ・関係）/ 不変条件（番号付き） |
| 静的構造 | モジュール構成（責務）/ 許可依存（モジュール間依存ルール） |
| 動的構造 | シナリオ別シーケンス |

それ以外は**ビュー**として manifest で有効化する: ユースケース、画面設計、API surface、データ設計、データフロー、イベントカタログ、外部連携、権限モデル、配置構成。

各アーティファクト型は次を宣言する:

- **リンク義務** — 何を参照しなければならないか（例: 動的構造の登場要素は静的構造に解決される、画面はユースケースに接続する）
- **前提ビュー** — 有効化の依存（例: 画面はユースケースが有効でなければ enable 不可）

閉包検証は「**有効な型のリンク義務がすべて解決すること**」と定義する。これにより閉包の定義は一つのまま成果物集合が可変になる。

プロジェクト種別プリセット（web-app 等）は「ビュー有効化セットの糖衣」として後付けできるものとし、独立した機構にしない。

**扱わないもの**（実装レイヤの領分）: 振る舞いの詳細仕様（Gherkin 的網羅）、タスク分解・工程計画、テスト設計。ユースケースは「アクター + ゴール + 粗い主フロー」で止める。

## Consequences

- コアが常在するため、request 導出の足場が全プロジェクトで共通になる
- ドメインが薄いプロジェクトは薄く書けばよい。「薄い」と「無い」は違う。コアまで optional にすると閉包の足場が消える
- ビュー型の追加はツール側の実装を要する（ユーザー定義型は必要になった証拠が出るまで作らない）
