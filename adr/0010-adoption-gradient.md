# ADR-0010: 導入の段階性 — 最小プロファイルは静的構造のみ

- Status: accepted（ADR-0002 を修正する）
- Date: 2026-07-02

## Context

既存プロジェクトには、自前の設計運用が既に回っているものがある。実例として、実装パイプラインのプロジェクト自身が architecture フォルダ（静的構造 + 番号付き不変条件 + それを grep で機械検証する architecture test）だけで設計と実装の整合を保ち続けている。ドメイン文書も動的構造も topic ループも持たずに、である。

ADR-0002 は「コア 3 層は常時有効・必須」と定めたが、フル 3 層 + ループ一式を導入の前提にすると、こうした「既にうまく回っている」プロジェクトには置き換えコストだけが立ち、採用されない。「install してすぐ使える」は、最初の成果物 1 枚で価値が出ることを要求する。

また閉包の定義（ADR-0002: 有効な型のリンク義務がすべて解決すること）は、有効集合が縮んでも壊れない。「コア必須」は閉包機構の要請ではなくポリシーであった。

## Decision

- **最小プロファイルを「静的構造（モジュール構成 + 許可依存）のみ」とする**。これだけで出口ゲート（`export rules` → architecture test）が成立し、単体で価値が出る
- ドメイン・動的構造は「強く推奨されるコア」に格下げし、manifest で段階的に有効化する。ADR-0002 の「常時有効・必須」を本 ADR で修正する
- 有効化の段階の目安:
  1. 静的構造 + 許可依存 — 歯だけ欲しい（architecture フォルダ運用の形式化）
  2. + ドメイン・動的構造 — 設計の閉包
  3. + topic / plan / 要素状態機械 — 設計継続ループの全体
  4. + ビュー — プロジェクト性質に応じた拡張
- 既存の設計文書を持つプロジェクトの導入経路は、置き換えではなく**その場での形式化**とする: 既存文書に ID を振り、strict プロファイルに寄せ、手製の機械検証があれば rules export に差し替える
- 各段階は**単体で完結した価値**を持たねばならない。次の段階が前提の機能を前の段階に混ぜない

## Consequences

- 閉包は段階ごとに「その段階での正しさ」を持つ。用語解決はドメイン有効時のみ、request 導出の引用は有効な層の要素に限られる。この段階依存の意味論を形式仕様に明記する
- ツールの価値が分解可能になる: 歯パイプライン単体 / 設計の閉包 / フルループ。それぞれ独立に採用・評価できる
- 段階①のプロジェクトが実在する前提でコマンド群を設計する。status は縮退集合では**算出可能なフロンティアのみ**に退化する: loop 無効時は「state.json 不在 = 全要素 designed」の縮退により designed フロンティア（= 有効型の全要素の一覧）だけが意味を持ち、topic / requested のフロンティアは現れない。**loop 前提の動詞（plan / coverage / derive / mark）は段階③で初めて有効**であり、それ未満の段階では明示的なエラーで案内する（縮退して動くふりをしない）
