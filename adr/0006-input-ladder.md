# ADR-0006: 入力の階段 topic → design → plan → request

- Status: accepted（本文中のファイル名例 `design/topics/<id>.md` は形式仕様の確定により `topics/<slug>.md`（slug 基準）に統一された。命名は spec/format.md §2 が正。plan の永続性と topic の `status` frontmatter は ADR-0018 で修正された）
- Date: 2026-07-02

## Context

成果物の形式の厳密さは「下流に人がいるか」で決まる。実装 request が精密でなければならないのは、下流が無人パイプラインであり、設計分岐を事前に潰さないと迷走するからである。設計への入力は attended セッションが曖昧さを吸収できるため緩くてよい。ただし受け皿（バックログ）とトレーサビリティのアンカーは必要になる。

GitHub issue を入力の正本にするとプラットフォーム依存になり、汎用ツールの方針に反する。

また、設計差分から request への束ね方（統合・分割・順序・並列可否）は機械的合否が存在しない判断であり、かつ「AI が request 本文を書いた後に人が束ね直す」流れでは高価な成果物の書き直しが発生する。

## Decision

成果物の階段を次で固定する。下流ほど形式が硬くなる:

| 段 | 形式 | 硬さの理由 |
|---|---|---|
| topic | 症状・動機（+ 任意で意図）。数行 | 下流が attended |
| design | ID・参照・閉包を持つ構造化文書 | 機械の読者がいる |
| plan | 要素の束ね方の表 | 判断の置き場。coverage が検証 |
| request | 精密なテンプレート | 下流が無人 |

**topic**:

- `design/topics/<id>.md`。frontmatter に `status: open → addressed` と `source:`（出所への逆リンク: issue / 監査 / フィードバック / 思いつき）
- 起点は二系統: **人起点**（意図を書いてよい。ただし提案であって決定ではなく、決定の正本は ADR）と**パイプライン起点**（実装工程で出た設計レベルの摩擦 — レビューの構造指摘・スコープ外 finding 等 — が機械的に排出される）
- 設計 delta の ADR は **topic の引用を必須**とする（閉包規則）。「なぜこの設計変更をしたか」のトレースを構造的に途切れさせない

**plan**:

- `plan` コマンドが designed 要素を表に吐き、**人が統合・分割・順序・並列可否を編集**する。判断は request 本文生成の前に置く
- ツールは判断材料を注釈する: 要素間の依存辺（順序制約）、モジュール接地（並列実行の衝突警告）、in-flight request との重複（既に requested の要素）
- `coverage` が機械検証する: **plan の全要素**の request 草稿への被覆（母集合は ADR-0005 と同一。plan に載せなかった designed 要素は不合格要因ではなく、status のフロンティア「起票待ち」に残る）、引用 ID の実在、依存辺と並列指定の矛盾
- plan は永続する横断アーティファクトとし、「なぜこの束で切ったか」の記録を兼ねる

## Consequences

- 設計バックログがプラットフォーム非依存になり、status が open topic を常時可視化する
- トレースが topic → ADR → 要素 → request → PR で途切れない
- 微修正にも topic 1 ファイルを要求する官僚性は許容する（3 行で書ける）
- request 本文の生成は束ね方確定後の 1 回で済む
