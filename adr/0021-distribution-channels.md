# ADR-0021: 配布チャネル — npm と単一バイナリの二正面、bun-native の維持

- Status: accepted
- Date: 2026-07-04

## Context

aozu は npm（`@color4pen/aozu`）に公開済みだが、現行の配布は「TS ソース直配布・bun ランタイム必須」であり、次の二つの事実と緊張がある:

1. **対象者は言語非依存**。aozu が管理するのは任意言語のリポジトリの設計文書であり、JS ツールチェーンを持たない開発者（Python / Go / Rust 等のプロダクト）も本来の観客である。npm 配布だけでは、この層は導入の壁に当たった時点で黙って離脱し、需要として観測されない
2. **Bun API への依存はベンダーロックイン**。コードが Bun API 面で書かれているため、Node 単独環境では動かない。Node API 面へ移行すれば npm チャネルの互換は最大化するが、ゼロビルド（TS 直配布）とゼロ依存の単純さを失う

検討の過程で、`bun build --compile` による単一バイナリ（ランタイム同梱・クロスコンパイル可）が「JS ツールチェーンを持たない層」への到達手段として成立し、Node API 移行の主根拠（観客の取りこぼし）を吸収することが判明した。

## Decision

1. **二正面配布を正とする**: npm（JS エコシステム向け、`bunx` / グローバルインストール）と、GitHub Releases に添付する単一バイナリ（言語非依存層向け、ランタイム不要）。バイナリは `bun build --compile` でクロスコンパイル（macOS arm64/x64・Linux x64/arm64・Windows x64）し、release-please のリリースに自動添付する。導入用の `install.sh` を提供する
2. **プロジェクトの形は bun-native を維持する**（ADR-0009 の再確認）: Bun API・ビルドなしの TS 直配布・bun ツールチェーン。単一バイナリは bun ランタイムを同梱するため、Bun API のままコンパイルできる
3. **Node API 面への移行は保留**（却下ではない）。再検討トリガーを明示する: (a) bun プロジェクトの健全性・継続性に具体的な兆候が出たとき、(b) 「npx / devDependency の形でしか導入できない」具体的な消費者が現れたとき。移行時の構成も記録しておく: コードを Node API 面に置換 + `bun build --target=node` で dist 化 + Bun API 逆流を防ぐ grep の歯（実装パイプラインの `grep-no-bun-imports` と同型）

## Alternatives Considered

### Node API 面への移行を先に行う

- **Pros**: npm チャネルの互換が最大（npx / Node-only CI で動く）。単一ベンダーランタイムへの保険
- **Cons**: ゼロビルドを失い、Bun API の置換コストを observable な需要なしに前払いする
- **Why not**: 主根拠だった「観客の取りこぼし」は単一バイナリチャネルが吸収する。残るベンダーリスクは低確率かつ事後移行で回復可能な障害（設計文書は無傷、ツールの書き換えのみ）であり、保険料の前払いに見合わない

### npm のみ継続

- **Pros**: 追加インフラなし
- **Cons**: 言語非依存の観客に届かない。離脱は観測不能（silent churn）で、需要駆動の判断材料が永遠に集まらない
- **Why not**: 公開ツールでは「要望が来ないこと」は「需要がないこと」を意味しない

## Consequences

- バイナリは 1 ターゲット 60〜90MB（ランタイム同梱の宿命）。開発者ツールとして許容圏
- publish workflow にコンパイル matrix と release 添付が加わる（一度組めば自動）
- `--version` フラグが版数確認（インストーラ・presence 検証）の前提になる（実装済み）
- Homebrew tap 等の追加チャネルは需要が観測されてから（本 ADR の二正面で入口は覆われている）
