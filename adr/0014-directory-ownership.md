# ADR-0014: ディレクトリの所有権 — 正本にツール名を冠しない

- Status: accepted
- Date: 2026-07-02

## Context

設計文書ディレクトリの命名に二つの流儀がある。エコシステムの先行ツール（実装パイプライン・仕様管理ツール）はツール名を冠したディレクトリ（`specrunner/`、`openspec/`）を使っており、同じ慣習に合わせる選択肢があった。また本ツールは `state.json` や `rules.json` を設計ディレクトリ配下に書き込むため、「ツールの作業場」として扱う余地もあった。

## Decision

設計ディレクトリは **`design/`（ツール名を冠しない）** とする。

判定基準: **そのディレクトリはツールが死んだ後も意味を持つか。**

- ツール名を冠するのが正しいのは**ワークフローの経緯**（drafts / changes / job 成果物）まで。それらはツールと運命を共にする
- `design/` の中身は**プロダクトの正本**である。設計文書・topic（設計バックログ）・plan（束ね方の判断記録）・`state.json`（要素↔request↔PR のトレース）・`rules.json`（歯の供給源）はいずれも、同じ形式を読む別ツールに乗り換えても意味を保つ
- 判定基準は「誰が書くか」ではない。`state.json` はツールのみが書くが、書き込まれる中身は作業の途中状態ではなくトレースの正本である
- derive が生成する request 草稿は正本ではなく実装パイプラインへの入力なので、`design/` に置かず設定された出力先（パイプラインの領地）へ輸出する（ADR-0012 と整合）

brownfield で既存の `design/` ディレクトリと衝突する場合は `--dir` フラグと manifest 検出（`design/manifest.md` の有無）で回避する。

## Consequences

- 形式と知識がツールブランドから独立し、ツールは「正本の読者の一人」に位置づけられる
- エコシステム内で見た目の一貫性は失う（同一リポジトリに `specrunner/` と `design/` が並ぶ）が、これは中身の性質の違い（経緯 vs 正本）を正しく表現した結果である
