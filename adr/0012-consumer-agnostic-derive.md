# ADR-0012: 導出の消費者非依存 — request テンプレートは注入する

- Status: accepted
- Date: 2026-07-02

## Context

plan / coverage / derive の最終成果物は request 文書であり、これは実装パイプライン（例: spec-runner）の契約物である。つまり導出の出口は本質的に消費者固有になる。これをツールにどう持たせるかには三つの形がある:

1. 消費者別のサブコマンド（`derive --for <pipeline>`）を持つ — ツールが消費者を知ることになり、境界原則（ADR-0001: 連携はファイルと CLI 契約のみ）が壊れる。新しいパイプライン対応のたびに本ツールの変更が要る
2. 橋渡し専用の別ツールを作る — 消費者が一つの段階では過剰な分割で、リポジトリと契約が一組増えるだけ
3. 消費者固有性を設定に閉じ込め、コマンドは汎用のまま保つ

## Decision

案 3 を採る。**derive は消費者を知らない**。

- request テンプレートは設定で注入する: `request-template`（テンプレートを出力するコマンドまたはファイルパス。例: `specrunner request template`）。`prompt derive` はこれを実行・読込して指示に含める
- 草稿の出力先も設定で指定する: `request-output-dir`（例: 実装パイプラインの drafts ディレクトリ）
- 草稿の成形（テンプレートへの当てはめ）は指示を受けた agent の仕事であり、ツールはテンプレートの構造を解釈しない
- `coverage` は草稿中の `[[id]]` 引用のみを検査する（形式仕様 §6 の一文法）。テンプレートが何であれ検査は変わらない

消費者固有性は設定 2 点（テンプレート源・出力先）に閉じる。

## Consequences

- 本ツールは spec-runner を知らないまま spec-runner の役に立つ。別のパイプラインへの対応は設定変更のみで、ツールの変更を要しない
- テンプレートが要素引用の記法（`[[id]]`）を受け入れられることだけが暗黙の前提になる。受け入れられない消費者では coverage が機能しない — この前提は交換面契約に明記する
- 消費者別サブコマンドを求める声が出た場合は、まず設定プリセット（名前付き設定の同梱）で応え、コマンド分岐はしない
