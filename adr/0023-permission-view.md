# ADR-0023: permission ビューの追補 — 表面非依存の操作 × アクター表と突合契約

- Status: accepted
- Date: 2026-07-10

## Context

ADR-0022 はビュー型の追補を named consumer 駆動と定め、permission を一件目の有力候補と予告した（consumer 候補 = 権限マトリクスとコード定義の突合テスト）。その named consumer が立った: clearflow（業務 SaaS）は 12 エンティティ × 操作 × 4 ロールの権限マトリクスを `src/domain/authorization.ts` に一元定義しており（deny-by-default の `canPerform(role, entity, operation)`）、資産マップに「permission ビュー = マトリクスとコード定義の突合テスト。ビュー型実装時に有効化」と予約済みである。

実地調査（2026-07-10）で需要の質も確認した:

- **同一マトリクスに対し、UI（生ロール判定の直書き）と MCP ツール（canPerform 経由）で実効アクセスが食い違う箇所が実在する**。認可の失敗は沈黙し（誰にも見えないまま稼働し続ける）、突合だけが機械的に炙り出せる
- マトリクスの記述が ①コードの一元定義（機械可読）②設計文書の表（人間可読・参考）③テストのハードコード期待値、の 3 箇所に分散している。突合契約が立てば ① を正本に ②③ を畳める
- 操作語彙が型検証されず（`operation: string`）、タイポや未定義操作は deny-by-default に黙って吸収される。設計側の操作列挙が立てば機械検出できる

本 ADR はビュー型追補の機構そのもの（ADR-0022-3: 宣言構文・リンク義務・C6 結線・前提表の確定を最初の型で検証する）を確定する役割を兼ねる。

## Decision

### D1: perm 要素は「保護対象ごとの権限ブロック」を単位とする

1 見出し 1 perm 要素 = 1 つの保護対象（エンティティ等）の操作 × アクター表。粒度の根拠は ADR-0017 — perm の主たる引用文脈は「この対象の権限を変える」という topic / request であり、対象単位が引用される最小単位になる。行単位（対象 × 操作）は細かすぎて引用が散り、マトリクス全体の一枚では引用が意味を失う。

### D2: 操作行の文法は表面非依存とする

機械の読む正本は操作行 `- <operation>: [[act-id]](, [[act-id]])*`。operation はプロジェクトの語彙（自由トークン）であり、**その操作が画面・API・MCP ツールのどの表面から呼ばれるかを perm は知らない**。表面 → 操作の対応はコード側の関心事で、各表面が同じ表に対して突合する。一件目のプロジェクトが UI と MCP の両表面を持つ事実が、この非依存性をスキーマに強制する（screen を焼き付けない）。

### D3: 参照義務は act のみ、前提層は domain に確定

操作行の参照はすべて act 要素に解決されること（C5 の主語義務と同型の適格性検査）。`対象:` 行（任意）は任意の実在要素を指せる（解決検証は C3 の一般規則）。act は domain 層に属するため、permission の前提を static から **domain** に確定する（§3 の暫定表の確定。domain は static を前提に含むため推移的に satisfies）。

### D4: 消費インターフェースは `export permissions`

突合テスト（named consumer）が Markdown パーサを自作させられる構図を避けるため、`export permissions` が中立 JSON を排出する（rules export と同じ考え方）。コミット済み成果物と `--verify` は持たない — 突合の比較対象はコード側の権限定義そのものであり、中間成果物を挟む必要がない（消費側テストは devDependency の aozu を直接実行できる）。出力順は決定的（id 昇順・operation 辞書順・act ID 昇順)とし、diff の安定性を保証する。

### D5: scaffold は対象外

perm は見出し宣言型（mod / ent / act と同族）であり、document 型（topic / plan / seq / adr）にのみ存在する scaffold の対象にしない。ビュー型追補の機構としても「scaffold はドキュメント型の追補時のみ」を前例とする。

### D6: C11 に views の参照方向を追加する

views の要素は static / domain / dynamic の要素を参照できる（下位層への参照のみ）。逆方向（コア 3 層 → views）は禁止 — コア層はビューの有無から独立している（ADR-0002 の成果物モデルを壊さない）。

### D7: 縮退と fail-closed は既存規則の一貫適用

permission が enabled でないときの perm 宣言は「既知だが無効な型」として C3 と同じ縮退に従う（評価除外）。enabled に現れた**未サポート**のビュー型は従来どおり C6 違反（fail-closed 不変）。C6 は「サポート型はリンク義務を検証し、未サポート型は常に違反」の二相になる。

## Alternatives Considered

### 行粒度（対象 × 操作 = 1 要素）/ マトリクス全体（1 要素）

- **Pros**: 行粒度は参照の解像度が最大。全体一枚は書き起こしが最速
- **Cons**: 行粒度は clearflow 実測で 60+ 要素になり引用が散る。全体一枚は「invoice の権限を変える」request が全マトリクスを引用することになり、被覆の意味が消える
- **Why not**: ADR-0017 の基準（引用される最小単位）に対象単位が最も合う

### operation の語彙をスキーマ側で型として固定する

- **Pros**: 操作名のタイポを aozu の check が直接検出できる
- **Cons**: 操作語彙はプロジェクト固有で、ツールが列挙を持つと ADR-0002 の「型はツールの知識」が「操作もツールの知識」に滑る。表面非依存も壊れる
- **Why not**: 語彙の固定はプロジェクト側の突合テストが担える（設計側の列挙 vs コード側の列挙の等値検査）。ツールは形（行文法）だけを検証する

### `--verify` つきのコミット済み permissions.json

- **Pros**: rules.json と対称になる
- **Cons**: rules の消費者（architecture test）は「設計 vs 実装 import」の突合で、コミット済み ruleset が比較の土台になる。permissions の消費者は「設計 vs コードの権限定義」の直接突合で、中間成果物は比較対象を増やすだけ（3 冊目の帳簿）
- **Why not**: 帳簿は 2 冊（設計・コード）で足りる。export は突合の瞬間にだけ存在すればよい

### 表面（screen / MCP tool / endpoint）を perm の属性に持つ

- **Pros**: 「どの画面から呼べるか」まで設計層で見える
- **Cons**: 表面 → 操作の対応はコードの構造（ルーティング・ツール登録）そのものであり、設計層に複製すると腐る（ADR-0004）。スキーマに screen が焼き付き、MCP だけのプロジェクトで空欄のセレモニーが生まれる
- **Why not**: 表面はコード正本。設計層は操作 × アクターの意図だけを持つ

## Consequences

- ビュー型追補の機構（enabled 受理・per-type リンク義務・§8 スキーマ追補・§3 前提確定・C6 二相化）が一件目で検証される。以後の型は同じ手順で個別に追補する（ADR-0022-3）
- clearflow は adoption Step 4（permission 有効化・マトリクス書き起こし・突合テスト結線を同一 PR）に進める。UI と MCP の食い違いが最初の突合で顕在化する見込み
- 加算的変更であり format-version は不変（ADR-0022-5 / ADR-0016）
- 未サポートのビュー型の扱い・prefix 予約の意味論は変わらない（ADR-0022）
