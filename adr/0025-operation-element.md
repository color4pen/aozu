# ADR-0025: Operation 要素 — 操作語彙を参照可能な第一級要素へ昇格する

- Status: accepted
- Date: 2026-08-14

## Context

permission ビューの操作は自由トークンである（ADR-0023 D2: `- <operation>: [[act-id]]...`）。ADR-0023 は Context でその帰結を記録している: 操作語彙が型検証されず、タイポや未定義操作は deny-by-default に黙って吸収される。**設計側の操作列挙が立てば機械検出できる**——この予告が本 ADR の起点である。

同時に、設計から実装骨格を静的生成する下流ツール（generator）の需要が立った。generator が読むべきは「システムが提供する操作の境界」——どの操作が存在し、何を対象とし、どこに接地するか——であり、現状この情報は perm の自由トークンと散文にしか存在せず、参照も export もできない。

なお ADR-0023 が却下した「操作列挙の型検証」は**ツールが列挙を持つ**案であり（「操作もツールの知識」に滑るため却下）、プロジェクトが design/ に列挙を書くことを妨げない。語彙の所有をプロジェクトに残したまま参照可能にする形が、却下理由と両立する残された道である。

## Decision

1. **op 型の追加**（domain 層・見出し要素）。機械が読むのは **ID・表示名（見出し）・任意の `対象:` 行（domain 要素への参照、カンマ区切り）・任意の `実装:` 行**（mod と同じ文法）のみ。それ以上を持たない: 入出力・事前条件・分岐・処理の流れは op の語彙に含めない。**op は「この操作が存在する」という境界の宣言であり、振る舞いの内容は実装コードの領分**である
2. **perm 操作行の op 参照化**: 操作行を `- [[op-id]]: [[act-id]](, [[act-id]])*` に改め、自由トークンを廃止する。op 参照は C6 のリンク義務（解決必須・同一 perm 内で一意）。これにより未定義操作・タイポ・削除済み操作への参照が check で機械検出される（ADR-0023 Context の予告の回収）。操作の表面非依存（どの画面・API・MCP ツールから呼ばれるかを設計は知らない — ADR-0023 D2）は op が引き継ぐ
3. **`export operations` の追加**: 操作境界の中立形式（id / name / target / implementation の決定的 JSON）を排出する実行時交換面。stdout または `--out`。**コミット済み成果物と `--verify` は持たない**——消費者（generator）は export を直接呼ぶ（permissions export と同じ判断 — ADR-0023 D4）。seq 等の相互作用情報は含めない
4. **format 0 内改訂**: 操作行の文法変更は破壊的だが、format-version は増分しない。根拠は二段: format v0 は dogfooding による修正を前提とした draft であり（spec/format.md Status）、この変更はその安定性契約の範囲内である。かつ旧文法の有効な corpus / consumer が存在しない（permission ビューを有効化した design が存在しない）

## 却下した代替案

- **操作列挙をツールが持つ**: ADR-0023 で却下済み。本決定でもツールが知るのは型 `op` だけであり、語彙（どの操作が存在するか）はプロジェクトが design/ に書く
- **自由トークンの維持 + 未定義操作の警告**: 未定義を判定するには設計側の列挙がどのみち必要であり、列挙が立つなら参照文法（`[[id]]`）に載せない理由がない。警告止まりは fail-closed に反する
- **op への入出力・事前条件・遷移の付与**: 操作の内容記述は独自の振る舞い記述言語に向かう。名指しできる読む機械（perm のリンク義務・generator の骨格生成）が読むのは境界（存在・参照・接地）までであり、内容の形式化は ADR-0004 の関門を通らない。必要が実測されたら個別に判断する（open-questions 論点 17）
- **uc / scr の同時削除**: op（何ができるか = 操作境界）と uc（何のためにどう使うか = 利用文脈）は別軸であり、op の導入は uc の存否に判断を与えない。型の削除には移動先の実在という独立の根拠を要する（論点 17）。変更理由の異なる判断を一つの改訂に混ぜない

## Consequences

- spec/format.md 改訂: §2 配置・§4 型表・§5 見出し要素・§8 op スキーマと perm 操作行・C6・§11 operations export
- 実装触点: parser（op 宣言・`対象:`・`実装:`）、check（C6 の perm 操作行 → op / act 義務）、`export operations`
- perm 操作行の旧文法（自由トークン）は不合法になる。移行対象の corpus は存在しない
- export の対象は操作に止まらない。generator は ent / inv / perm も読む想定であり、要求された型から順に同型の per-type export（rules / permissions / operations と同じ契約形）を需要駆動で追補する。複数型を単一の統合 export に束ねるかは消費者の実形が決める（論点 17）
- dogfooding（aozu 自身・clearflow の permission 有効化）で最小スキーマの十分性を実測する。入出力の要否・seq の意味論と登場要素への op 追加（C5）・利用文脈（uc）の去就は、実測後の論点として open-questions 論点 17 に置く
